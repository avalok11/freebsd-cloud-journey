# Конфиги нод стенда

Эталонные конфиги FreeBSD-нод учебного стенда. Появились в Фазе 2, когда
`fbsd-1-sel` выбыла и пришлось разворачивать `fbsd-3-sel` с нуля
(см. [`docs/phase-2/00-fbsd-3-sel-provisioning.md`](../docs/phase-2/00-fbsd-3-sel-provisioning.md)).

## Зачем это нужно

Две причины, обе про скуку, а не про красоту:

1. **Переиспользование.** Настройка новой ноды занимает полдня. Если конфиги лежат
   в git, следующая нода настраивается копированием файлов, а не повторением
   ручных правок — иначе через месяц у нас будет три разных «одинаковых» ноды.
2. **Ansible в Фазе 4.** Роль Ansible — разложить конфиги. Роль пишется по этим
   файлам, а не по памяти. То, что здесь лежит, — это то, что роль должна
   положить на ноду.

## Куда это пойдёт дальше

| Репозиторий | Что там | Статус |
|---|---|---|
| `freebsd-cloud-journey` (этот, GitHub, публичный) | описание проекта, отчёты, **эталонные конфиги лабораторного стенда** | здесь |
| `infra-configs` (Gitea, приватный) | боевые конфиги заказчика, роли Ansible, Bastillefiles, HAProxy, секреты в Ansible Vault | Фаза 4 |

Политика разделения зафиксирована в `docs/roadmap.md` → «Окружения и стенды».
Лабораторный стенд — не заказчик: его адреса из RFC 1918 и имена хостов
`*.lab.sel` ничего не раскрывают. Конфиги **заказчика** в публичный репозиторий
не попадают никогда.

## Структура

```
config/
  README.md
  fbsd-3-sel/                  # конфиги конкретной ноды
    README.md                  # что применено, что отличается, что исправить
    etc/
      issue.net
      pam.d/sshd
      pf.conf
      rc.conf
      resolv.conf
      ssh/sshd_config.d/00-hardening.conf
```

Путь внутри `etc/` **совпадает с путём на ноде**. Файл
`fbsd-3-sel/etc/ssh/sshd_config.d/00-hardening.conf` кладётся на ноду как
`/etc/ssh/sshd_config.d/00-hardening.conf`.

## Инвариант: «как применено»

Файлы лежат в том виде, в каком они **реально применены на ноде**. Не в том, в
каком «должно быть».

Причина: конфиг-репозиторий должен отражать состояние, иначе расхождение
между git и нодой становится невидимым. Отклонения от целевого состояния
фиксируются **в README ноды** — с точным описанием, что исправить и когда.

Это не значит «никогда не править». Значит — правка и применение идут вместе:
исправил на ноде → обновил файл здесь → отметил в README.

## Чего здесь нет и почему

| Не хранится | Где вместо этого |
|---|---|
| Приватные ключи (`ssh_host_*`, `freebsd_lab`, `zfs_repl`) | на нодах, в `~/.ssh/` с `chmod 600`; бэкап в KeePassXC |
| Сертификаты (`*-cert.pub`, `user_ca.pub`, `host_ca.pub`) | выпускаются CA на `fbsd-ca-sel`, копируются на ноды |
| CRL (`revoked_keys`) | генерируется на CA, раздаётся на ноды |
| Пароли, TOTP-секреты | в KeePassXC; в Ansible — Ansible Vault |
| Ключ шифрования `tank-secure.key` | в KeePassXC, per-host |

## Ноды

| Нода | Каталог | Статус |
|---|---|---|
| `fbsd-3-sel` | [`fbsd-3-sel/`](./fbsd-3-sel/) | активен, развёрнут 2026-10-27 |
| `fbsd-1-sel` | — | выбыла (нет ресурсов в Selectel) |
| `fbsd-2-sel` | — | активна, конфиги отличаются (нет TOTP, jump-only) |
| `fbsd-ca-sel` | — | активна, только sshd + CA |
| `fbsd-arm` | — | локальная UTM arm64, свой набор |
