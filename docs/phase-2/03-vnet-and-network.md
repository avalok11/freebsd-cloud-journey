# VNET: как jail получает свою сеть

**Цель:** понять, что именно изолирует VNET, как устроена связка `bridge` + `epair`,
и почему без NAT на хосте jail в интернет не выйдет.

**Ключевой тезис.** Jail без VNET **делит сетевой стек с хостом** — получает
IP-алиас и живёт в общей таблице маршрутизации. Jail с VNET получает **свой
сетевой стек целиком**: свои интерфейсы, свои маршруты, свои правила firewall, свой
loopback. Это принципиально разные уровни изоляции.

## Три способа дать jail'у сеть

| Способ | Изоляция | Что видит jail | Когда применять |
|---|---|---|---|
| **IP-алиас** (без VNET) | нет | общий сетевой стек хоста | быстрые тесты, jail без сети наружу |
| **bridge + epair** (VNET) | полная | только свой `epair` | рабочий вариант, то, что делает Bastille |
| **Netgraph** | полная | свой `ng`-интерфейс | сложные сценарии с несколькими мостами |

Мы используем второй.

## Анатомия VNET-схемы

Вариант, который мы строим: **мост — только для jail'ов, физический интерфейс в
мост не входит**. Хост маршрутизирует трафик jail'ов сам и нататит его.

```
                       хост (fbsd-3-sel)                     jail (web)
  ┌────────────────────────────────────────┐   ┌───────────────────────────┐
  │                                        │   │                           │
  │   vtnet0  172.16.0.5/16 ───────┐       │   │   epair0b                 │
  │        (единственный адрес     │       │   │      (виртуальная NIC)    │
  │         ноды, в мост НЕ входит)│       │   │           │               │
  │                                 │       │   │   lo0 (свой loopback)    │
  │                                 ▼       │   │           │               │
  │   ┌──────────────────────────┐  │       │   │   своя таблица           │
  │   │ bridge0  10.10.10.1/24   │  │       │   │   маршрутизации,          │
  │   │  (шлюз jail'ов)          │  │       │   │   свой PF                 │
  │   │      │                   │  │       │   │                           │
  │   │      └── epair0a ────────┼──┼───────┼──▶│                           │
  │   └──────────────────────────┘  │       │   └───────────────────────────┘
  │                                 │       │
  │   PF: nat on vtnet0 from 10.10.10.0/24   шлюз Selectel
  │        → 172.16.0.5 ; форвардинг 1       172.16.0.1
  └────────────────────────────────────────┘
```

- **`epair`** — пара виртуальных Ethernet-интерфейсов. Один конец (`epair0a`)
  живёт на хосте, второй (`epair0b`) переносится внутрь jail'а. Для jail'а это
  выглядит как обычная сетевая карта.
- **`bridge0`** — мост на хосте, в который добавлены **только** `epairNa` jail'ов.
  На самом мосте — адрес шлюза jail'ов `10.10.10.1/24`.
- **PF на хосте** — маршрутизирует трафик jail'ов (форвардинг), делает NAT (выход
  наружу) и `rdr` (входящие соединения).

Пара `epair` — ресурс: одна пара обслуживает один jail в данный момент.

### Почему `vtnet0` не входит в мост

Bastille в режиме `-V` (стандартный VNET) добавляет физический интерфейс в мост
через `jib`. Мы так не делаем, и вот почему:

1. **FreeBSD 15 это deprecated.** Handbook, раздел «VNET Jails»: адрес интерфейсу
   назначать нельзя, если интерфейс — член моста; адрес должен быть на самом
   мосте. На FreeBSD 15.0 ядро пишет об этом предупреждение, на FreeBSD 16
   будет отказ.
2. **У `vtnet0` — единственный адрес ноды** (`172.16.0.5/16`). Если адрес и
   интерфейс в мосте — нода рискует потерять связь с Selectel-сетью, а это
   единственный способ на неё попасть.
3. **Трафик в обход PF.** Если `vtnet0` — член моста, трафик jail'а к
   `172.16.0.1` идёт через L2-мост, минуя маршрутизатор хоста. При
   `net.link.bridge.pfil_bridge=0` (а именно это ставит `bastille setup bridge`)
   PF такой трафик вообще не видит: ни NAT, ни фильтрации.

Схема «мост без физического интерфейса» даёт три выигрыша сразу: адрес живёт на
мосте (не deprecated), форвардинг делает хост (значит, трафик виден PF), а
`bridge0` — чисто внутренний интерфейс.

## Предусловия

```sh
sysctl kern.features.vimage      # должен быть 1 — поддержка VNET в ядре
kldload if_epair
kldload if_bridge
```

Мост — persistent, и адрес шлюза jail'ов живёт на нём:

```sh
sysrc cloned_interfaces+='bridge0'
sysrc ifconfig_bridge0='inet 10.10.10.1/24 up'
```

### Про `net.link.bridge.pfil_*`

`bastille setup bridge` выставляет `pfil_bridge=0`, `pfil_onlyip=0`,
`pfil_member=0` — то есть PF перестаёт видеть bridged-трафик. **Мы этого не
делаем и sysctl'ы не трогаем**, потому что:

- трафик jail → интернет у нас **маршрутизируется хостом**, а не идёт bridged'ом;
  PF видит его в обычном inet-пути и с интерфейсом `bridge0` — независимо от
  значений `pfil_*`;
- при `pfil_bridge=1` (значение по умолчанию) PF видит и трафик **между
  jail'ами** — а его мы как раз блокируем правилом
  `pass in on $jail_if from $jail_net to ! $jail_net keep state`.

Ошибка, из-за которой `set skip on $bridge_if` предлагают как лекарство: если
в bridge входит `vtnet0`, jail-to-jail трафик идёт мимо маршрутизации хоста, и
`block in all` его срезает — отсюда и совет «skip на мосте». В нашей схеме
мост чисто внутренний, и `set skip` не нужен: достаточно одного явного правила.

## NAT: почему без него jail в интернет не выйдет

Jail с приватным адресом (на `lo1`, на мосту, на epair) **не имеет маршрута в
интернет по умолчанию**. Свой маршрут по умолчанию у него есть, но адрес назначения
не маршрутизируется в интернете — пакеты просто некуда уйдут.

Хост должен **транслировать** адрес jail'а в свой:

```sh
# форвардинг между интерфейсами
sysrc gateway_enable="YES"
sysctl net.inet.ip.forwarding=1

# в /etc/pf.conf
ext_if = "vtnet0"
nat on $ext_if from 10.10.10.0/24 to any -> ($ext_if:0)
```

**NAT — по подсети, а не по таблице `<jails>`.** Bastille наполняет таблицу
`<jails>` адресами jail'ов только для jail'ов **без** VNET: в `start.sh` (исходники
1.4.4) добавление в таблицу обёрнуто в проверку
`if [ "$(bastille config ${jail} get vnet)" != 'enabled' ]`. Для VNET-jail'а таблица
остаётся пустой, и правило `nat ... from <jails>` просто ничего не сделает.
Подсеть работает всегда.

Входящие соединения публикуются через `rdr` — это уже проброс порта:

```sh
rdr on $ext_if proto tcp to port 80 -> 10.10.10.10 port 80
```

`bastille rdr` для VNET-jail'ов **не работает** — `rdr.sh` заканчивается ошибкой
«VNET jails do not support rdr». Правило `rdr` пишем руками.

### Порядок действий

1. `bastille setup vnet` — единственный безопасный `setup`: ставит `jib` и пишет
   `/etc/devfs.rules` с `bastille_vnet=13`. PF не трогает.
2. Поднять мост и шлюз jail'ов (`bridge0`, `10.10.10.1/24`), включить форвардинг.
3. Применить наш ruleset с блоком jails: `pfctl -nf` (проверка) → `pfctl -f`.
4. `bastille create -B ...` — jail поднимется уже в готовой схеме.

> **Никогда не запускать `bastille setup` и `bastille setup firewall`.**
> `configure_pf` вставляет свой блок в начало чужого `pf.conf`, а в блоке —
> `block in all`. При first-match-wins это делает наши разрешающие правила
> мёртвыми: SSH перестаёт работать. Подробно —
> в [`02-bastille-vs-others.md`](./02-bastille-vs-others.md).

## Свой PF внутри VNET-jail

Отдельный приятный момент: jail с VNET может запустить **собственный** pf
со своим `pf.conf` — правила хоста его не касаются.

Для этого jail'у нужен `/dev/pf`, а он открывается через devfs-правило.
Bastille делает это на шаге `setup vnet`:

```sh
# /etc/devfs.rules
bastille_vnet=13
```

Внутри jail'а:

```
pf_enable="YES"
```

и свой `/etc/pf.conf`. Правила хоста и правила jail'а не пересекаются — это и есть
изоляция сетевого стека, а не просто отдельный адрес.

## Как Bastille всё это автоматизирует

`jib` (Jail Isolate Bridge) делает за нас: создаёт `epair` для jail'а, добавляет
хост-сторону в мост, поднимает интерфейсы, настраивает адрес и шлюз внутри
jail'а. Отсюда практический вывод: **нам не нужно писать сеть руками** —
достаточно правильно задать `bastille.conf` и параметры в Bastillefile.

Но две вещи Bastille делает не так, как нужно нам:

- **мост.** `setup bridge <if>` добавляет `<if>` в мост и вешает на мост
  адрес из `bastille_network_bridge`; при этом физический интерфейс оказывается
  в мосте вместе со своим адресом — ровно то, о чём выше. Мы мост создаём сами.
- **шлюз jail'а.** Без `--gateway` Bastille берёт шлюз маршрута по умолчанию хоста
  (`netstat -4rn | awk '/default/ {print $2}'` → `172.16.0.1`). Для нашей схемы
  шлюз jail'а — это `10.10.10.1`, адрес на мосте, поэтому его задаём явно:
  `--gateway 10.10.10.1` (или `bastille_network_gateway` в `bastille.conf`).

## Проверка изоляции (День 6 Фазы 2)

```sh
# изнутри jail: свой стек
bastille cmd web ifconfig
bastille cmd web netstat -rn

# снаружи: jail'а нет в списке интерфейсов хоста
ifconfig -a

# между двумя jail'ами: изолированы правилом `to ! $jail_net`
bastille cmd web ping -c2 <ip-другого-jail>

# выход наружу: работает только через NAT хоста
bastille cmd web ping -c2 8.8.8.8
```

Ожидание: изнутри видны только `lo0` и свой `epairNb`; хост не видит
интерфейсов jail'ов; два jail'а не видят друг друга; выход в интернет работает
через NAT.

## Сравнение с Linux

| | FreeBSD VNET jail | Docker (bridge) | Docker (macvlan) |
|---|---|---|---|
| Свой сетевой стек ядра | ✅ | ❌ (общий, разделены namespace'ом) | ❌ |
| Свой PF / iptables | ✅ | ❌ | ❌ |
| NAT делает хост | ✅ | ✅ (docker-proxy / iptables) | ❌ (адрес сразу в L2) |
| Jail видит MAC-адреса соседей | нет | нет | да |
| Два контейнера видят друг друга | нет | да (один bridge) | да |

Отличие, которое стоит запомнить: в Linux изоляция сети — это правила iptables и
разделение namespace'ов, а сам сетевой стек **общий**. В FreeBSD VNET — это
**отдельный экземпляр сетевого стека в ядре**, со своими правилами PF. Второй
уровень, а не первый.
