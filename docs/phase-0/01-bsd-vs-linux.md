## Два пути Unix-философии

FreeBSD и Linux — это два разных ответа на один вопрос: «как построить современную Unix-подобную ОС». Оба растут из классического Unix 70–80-х, оба дают тебе командную строку, демонов, файловую систему, сетевой стек. Но пути разошлись принципиально.

## 1. Архитектура ядра

**Linux — монолитное ядро с модулями.** Огромный кусок кода (`linux/kernel/`) содержит почти всё: планировщик, сетевой стек, драйверы, VFS, IPC. Драйверы и подсистемы можно загружать модулями, но они работают **в том же адресном пространстве, что и ядро** — упал модуль, упало всё ядро. Плюс: скорость (нет переключения контекста между ядром и модулями), огромная экосистема железа (любой китайский USB-адаптер скорее всего поддерживается). Минус: любая ошибка в модуле = паника ядра, security-баг в одном драйвере = уязвимость всего ядра.

**FreeBSD — монолитное ядро, но с принципиально другим подходом к модулям.** Базовое ядро (`GENERIC`) маленькое, содержит только критичные подсистемы. Всё остальное — модули: драйверы, файловые системы (ZFS, NFS, NTFS), сетевые подсистемы (PF, ipfw, netgraph), даже планировщики. **Дополнительная сила:** Capsicum — capability-режим для модулей и jail'ов, который ограничивает, что именно код может делать в ядре. Это даёт гранулярную защиту, которой в Linux исторически нет. Плюс: стабильность (битый модуль можно выгрузить без ребута), гибкость (можно собрать минимальное ядро для embedded). Минус: меньше драйверов «из коробки» для экзотического железа.

**Linux экспериментирует с микроядром:** есть eBPF, есть проекты вроде gVisor, есть попытки вынести драйверы в user-space. FreeBSD исторически идёт по пути модульности с capability-ограничениями.

## 2. Лицензия: BSD vs GPL

Это не юридическая формальность, это **философия**.

**FreeBSD — лицензия BSD (двух- и трёхпунктовая).** Разрешает всё: использовать в коммерческих продуктах, модифицировать, **закрывать исходный код** производных работ. Единственное требование — сохранить копирайт. **Не требует раскрытия изменений.**

**Linux — GPL v2 (для ядра).** Если ты взял код ядра и сделал производный продукт, ты обязан **раскрыть исходный код** под той же GPL. Это вирусная лицензия: связываешься с GPL-кодом — твой код тоже становится GPL.

**Что это значит на практике:**

- **Хочешь форкнуть FreeBSD, добавить проприетарные драйверы, продавать как закрытый продукт?** Свободно. Apple так делает с macOS (Darwin = XNU/Mach, не BSD целиком, но подход тот же). Sony PlayStation использует FreeBSD с закрытыми изменениями. С Linux так нельзя — обязаны открыть код.

- **Хочешь продавать роутер с Linux внутри?** GPL не запрещает продажу, но обязывает дать исходники по запросу. С BSD — никому ничего не должен.

- **Корпоративный compliance:** если у тебя контракты с NDA и запрет на раскрытие кода, **BSD-стек проще юридически**. Можно делать закрытые форки, не переживая про вирусность.

- **Для open source:** GPL — мощный инструмент защиты. Linux-код нельзя «присвоить» и закрыть. BSD-код может кто-то закрыть, но оригинал остаётся открытым.

## 3. Что это значит для нашего продакшена

**Когда BSD-стек выгоднее:**

- Делаешь **проприетарный продукт** на базе ОС (NAS, шлюз, облако).
- Важна **лицензионная чистота** для заказчика с жёстким compliance (финсектор, ФСТЭК).
- Нужна **предсказуемость** — меньше изменений в ядре, длинный цикл поддержки (RELENG).
- Хочешь **zfs/bhyve/jails** без «зоопарка» из разных проектов.

**Когда Linux выгоднее:**

- Нужна **поддержка специфического железа** (новейшее сетевое оборудование, GPU).
- Используешь **специфический софт**, который есть только под Linux (некоторые enterprise-приложения).
- Нужна **экосистема** (Kubernetes, Docker, огромная база драйверов).
- **Vendor support** важен (RHEL, SUSE дают коммерческую поддержку).

## 4. Наш выбор

Для проекта «FreeBSD Private Cloud» выбираем **FreeBSD как основу, Linux как дополнение**:

- **FreeBSD** — для ядра инфраструктуры: jails, ZFS, PF, CARP, lagg. Тут он сильнее.
- **Linux** — для прикладных сервисов, где есть готовые решения (например, k3s внутри jail, мониторинг, nftables для сравнения).

Это не «религиозный выбор», это **прагматика**: берём лучший инструмент под задачу, а не фанатично сидим на одной ОС.
