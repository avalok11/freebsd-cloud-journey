# Вертикальное vs горизонтальное масштабирование

**Время чтения:** ~5–7 минут
**Фаза:** 0 (вводная теория перед практикой)
**Цель:** понимать, как именно мы будем наращивать мощности, и почему для SMB выбираем гибрид.

---

## 1. Два базовых подхода

**Вертикальное масштабирование (scale up):**
- Увеличиваем ресурсы одной машины: больше CPU, больше RAM, больше диска.
- Пример: было 2 CPU / 4 ГБ, стало 8 CPU / 32 ГБ.
- Просто реализуется: поменял тариф у провайдера, перезагрузил.

**Горизонтальное масштабирование (scale out):**
- Добавляем новые машины в кластер, распределяем нагрузку.
- Пример: было 1 нода с приложением, стало 3 ноды за балансировщиком.
- Сложнее: нужна балансировка, репликация данных, консенсус.

## 2. Сравнение по критериям

| Критерий | Вертикальное | Горизонтальное |
|---|---|---|
| Стоимость | Дешевле до определённого предела, потом дорого (большие серверы = premium-цены) | Линейно масштабируется, можно начать с малого |
| Предел роста | Физический (самая большая доступная машина) | Почти бесконечен (добавляй ноды) |
| Отказоустойчивость | Нет — упала машина, всё упало | Да — упала одна нода, остальные работают |
| Сложность кода | Минимальная — один сервис, одна база | Высокая — репликация, консенсус, балансировка |
| Обслуживание | Простое — один сервер | Сложнее — кластер, мониторинг каждой ноды |
| Скорость изменений | Гибко у провайдера (почасовая оплата) | Нужно время на подключение ноды |
| Подходит для stateful | Да, отлично | Сложно, нужна репликация/распределённая ФС |

## 3. Что выбираем мы и почему

**Для SMB-облака — горизонтальное по дефолту, вертикальное по запросу.**

**Почему горизонтальное:**

1. **Отказоустойчивость.** У заказчика среднего бизнеса downtime = деньги. С master/backup или active/active одна нода может упасть, и сервис живёт. Это и есть наше «приватное облако» — оно должно переживать падения.

2. **Предсказуемость роста.** Заказчик не знает, сколько ему нужно через год. С горизонтальным масштабированием — добавил ноду, и всё. Без переезда на новый сервер.

3. **Технологический паритет.** Когда мы дойдём до Kubernetes (k3s) — там горизонтальное масштабирование встроено. Архитектура должна быть к этому готова.

4. **Бюджетная гибкость.** Можно начать с одной ноды, постепенно добавлять. С вертикальным — сразу нужно платить за «потолок».

**Когда всё-таки вертикальное (по запросу):**

- **База данных (PostgreSQL, MySQL)** — вертикально до предела. Один мастер, реплики только для чтения. Репликация PostgreSQL master-master — это боль, для SMB не оправдана.
- **ZFS storage нода** — вертикально: больше дисков в pool, больше RAM под ARC. Горизонтально распределённые ФС для SMB — избыточны.
- **Сервисы с состоянием**, которые не умеют кластеризоваться.

**Типичная схема:**
- **Application-ноды** (nginx, app, mail) — горизонтально. Можно 1, 2, 5 — без разницы, добавляем по нагрузке.
- **Database-нода** — вертикально до предела + read-реплики для тяжёлых запросов.
- **Storage-нода** — вертикально (диски, RAM).
- **Балансировщик** — обычно 2 ноды в CARP для HA.
- **Мониторинг/бэкапы** — отдельно, не на критическом пути.

## 4. Как это выглядит в нашей архитектуре

**Стартовая конфигурация (Фаза 0–1):**
```
1× fbsd-1-sel (gateway, всё на одной ноде, для теста)
```

**Рабочая конфигурация (Фаза 2–3):**
```
2× application-ноды за CARP/HAProxy
1× storage-нода с ZFS
1× Linux для мониторинга/k3s
```

**Production-конфигурация (Фаза 7–8, для заказчика):**
```
3× application-ноды (можно горизонтально добавлять)
2× gateway-ноды с CARP (отказоустойчивость L3)
2× database-ноды (master + replica)
2× storage-ноды (репликация между ними)
2× monitoring-ноды
```

**Что мы НЕ делаем:**
- Не строим «один большой сервер за миллион». Это не наш путь.
- Не автоматизируем шардирование БД и не делаем master-master для PostgreSQL. Для SMB это избыточно и ненадёжно.
- Не поднимаем Kubernetes-кластер на 20 нод. k3s на 3 ноды — это потолок для нашего сегмента.

## 5. Что выбрать прямо сейчас, при проектировании

| Решение | Выбор | Обоснование |
|---|---|---|
| Способ изоляции сервисов | Bastille (jails) | Горизонтально добавляются за минуты, нативно для FreeBSD |
| Способ хранения | ZFS на одной ноде (старт), реплика на вторую (через 2–3 месяца) | Вертикально + одна резервная нода, без распределённой ФС |
| Балансировка | HAProxy + CARP | Горизонтально, master/backup, failover за секунды |
| БД | PostgreSQL, одна нода + read-replica позже | Вертикально до предела, не master-master |
| Автоматизация | Ansible, всё в git | Декларативно, легко добавить новые роли/ноды |
| Мониторинг | Prometheus + Grafana на отдельной ноде | Горизонтально, не на критическом пути |
| Бэкапы | ZFS snapshot + Restic, выделенная нода | Вертикально, размер диска растёт по запросу |

## 6. Практический чек-лист: «масштабировать вертикально или горизонтально?»

Когда заказчик говорит «у нас тормозит», задай вопросы:

1. **Какой именно сервис тормозит?** (Один — вертикально, все — горизонтально).
2. **Есть ли состояние у сервиса?** (Если да — сложнее горизонтально, может проще вертикально).
3. **Какой утилизации CPU/RAM/IO сейчас?** (Под 80% — масштабируй; под 20% — ищи причину в коде).
4. **Можно ли разделить нагрузку?** (Чтение/запись, тяжёлые/лёгкие запросы — часто горизонтальное масштабирование через разделение).
5. **Сколько стоит downtime?** (Если high — горизонтально для HA, даже если текущая нагрузка не требует).

## 7. Типичные ошибки

**Раннее горизонтальное масштабирование:**
Заказчик поднимает 3 ноды, чтобы «было». Нагрузка — 5%. Получается: 3× расходы на обслуживание, мониторинг, бэкапы. **Лучше:** 1 нода с запасом, добавлять когда реально нужно.

**Игнорирование вертикального предела:**
PostgreSQL на одной ноде, база 2 ТБ, упираемся в IO. Решение — не «добавить ещё одну ноду с PostgreSQL», а «добавить RAM, перейти на NVMe, увеличить пул ZFS».

**Горизонтальное без автоматизации:**
3 ноды руками, потом ещё 3, потом ещё. Уже 9, а управляются копи-пастой. **Решение:** Ansible с первого дня, роли, инвентари.
