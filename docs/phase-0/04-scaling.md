# Вертикальное vs горизонтальное масштабирование

**Время чтения:** ~5–6 минут
**Фаза:** 0 (вводная теория перед практикой)
**Цель:** понимать, как именно наращивать мощности, и почему для SMB выбран гибрид.

---

## 1. Два базовых подхода

**Вертикальное масштабирование (scale up):**
- Увеличение ресурсов одной машины: больше CPU, больше RAM, больше диска.
- Пример: было 2 CPU / 4 ГБ, стало 8 CPU / 32 ГБ.
- Реализация: смена тарифа у провайдера, перезагрузка.

**Горизонтальное масштабирование (scale out):**
- Добавление новых машин в кластер, распределение нагрузки.
- Пример: было 1 нода с приложением, стало 3 ноды за балансировщиком.
- Требует: балансировка, репликация данных, консенсус.

## 2. Сравнение по критериям

| Критерий | Вертикальное | Горизонтальное |
|---|---|---|
| Стоимость | Дешевле до предела, потом дорого (большие серверы = premium) | Линейно масштабируется, можно начать с малого |
| Предел роста | Физический (максимально доступная машина) | Почти бесконечен (добавление нод) |
| Отказоустойчивость | Нет — упала машина, всё упало | Да — упала одна нода, остальные работают |
| Сложность кода | Минимальная — один сервис, одна база | Высокая — репликация, консенсус, балансировка |
| Обслуживание | Простое — один сервер | Сложнее — кластер, мониторинг каждой ноды |
| Скорость изменений | Гибко у провайдера (почасовая оплата) | Время на подключение ноды |
| Подходит для stateful | Да, отлично | Сложно, нужна репликация/распределённая ФС |

## 3. Что выбирается и почему

**Для SMB-облака — горизонтальное по дефолту, вертикальное по запросу.**

**Горизонтальное:**

1. **Отказоустойчивость.** У заказчика среднего бизнеса downtime = деньги. С master/backup или active/active одна нода может упасть, сервис продолжает работать. Это и есть «приватное облако» — оно должно переживать падения.

2. **Предсказуемость роста.** Заказчик не знает, сколько ресурсов понадобится через год. С горизонтальным масштабированием — добавил ноду, и всё, без переезда на новый сервер.

3. **Технологический паритет.** При переходе к Kubernetes (k3s) — там горизонтальное масштабирование встроено. Архитектура должна быть к этому готова.

4. **Бюджетная гибкость.** Можно начать с одной ноды, постепенно добавлять. С вертикальным — сразу оплата «потолка».

**Когда вертикальное (по запросу):**

- **База данных (PostgreSQL, MySQL)** — вертикально до предела. Один мастер, реплики только для чтения. Репликация master-master — боль, для SMB не оправдана.
- **ZFS storage нода** — вертикально: больше дисков в pool, больше RAM под ARC. Горизонтально распределённые ФС для SMB избыточны.
- **Stateful-сервисы**, которые не умеют кластеризоваться.

**Пример. Схема роста для заказчика:**

```
Старт (месяц 1):
  1× application-нода (всё на одной ноде)

Рабочая (месяц 3-6):
  2× application-ноды за CARP/HAProxy
  1× storage-нода с ZFS
  1× Linux для мониторинга/k3s

Production (после года):
  3× application-ноды (горизонтально)
  2× gateway-ноды с CARP (L3-отказоустойчивость)
  2× database-ноды (master + replica)
  2× storage-ноды (репликация между ними)
  2× monitoring-ноды
```

**Что НЕ делается:**
- «Один большой сервер за миллион» — не целевой путь.
- Шардирование БД и master-master для PostgreSQL — избыточно и ненадёжно для SMB.
- Kubernetes-кластер на 20 нод — k3s на 3 ноды это потолок для сегмента.

## 4. Решения при проектировании

| Решение | Выбор | Обоснование |
|---|---|---|
| Способ изоляции сервисов | Bastille (jails) | Горизонтально добавляются за минуты, нативно для FreeBSD |
| Способ хранения | ZFS на одной ноде (старт), реплика на вторую (через 2–3 месяца) | Вертикально + одна резервная нода, без распределённой ФС |
| Балансировка | HAProxy + CARP | Горизонтально, master/backup, failover за секунды |
| БД | PostgreSQL, одна нода + read-replica позже | Вертикально до предела, не master-master |
| Автоматизация | Ansible, всё в git | Декларативно, легко добавить новые роли/ноды |
| Мониторинг | Prometheus + Grafana на отдельной ноде | Горизонтально, не на критическом пути |
| Бэкапы | ZFS snapshot + Restic, выделенная нода | Вертикально, размер диска растёт по запросу |

## 5. Чек-лист «масштабировать вертикально или горизонтально?»

Когда заказчик сообщает о проблеме «у нас тормозит», задаются вопросы:

1. **Какой сервис тормозит?** (Один — вертикально, все — горизонтально).
2. **Есть ли состояние у сервиса?** (Если да — сложнее горизонтально, может быть проще вертикально).
3. **Какая утилизация CPU/RAM/IO сейчас?** (Под 80% — масштабировать; под 20% — искать причину в коде).
4. **Можно ли разделить нагрузку?** (Чтение/запись, тяжёлые/лёгкие запросы — часто горизонтальное масштабирование через разделение).
5. **Сколько стоит downtime?** (Если high — горизонтально для HA, даже если текущая нагрузка не требует).

## 6. Типичные ошибки

**Раннее горизонтальное масштабирование:**
Заказчик поднимает 3 ноды «чтобы было». Нагрузка — 5%. Итог: 3× расходы на обслуживание, мониторинг, бэкапы. **Решение:** 1 нода с запасом, добавлять когда реально нужно.

**Игнорирование вертикального предела:**
PostgreSQL на одной ноде, база 2 ТБ, упёрлись в IO. Решение — не «добавить ещё одну ноду с PostgreSQL», а «добавить RAM, перейти на NVMe, увеличить пул ZFS».

**Горизонтальное без автоматизации:**
3 ноды руками, потом ещё 3, потом ещё — итого 9, а управляются копи-пастой. **Решение:** Ansible с первого дня, роли, инвентари.
